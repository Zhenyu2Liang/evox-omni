# Demo 人工接管

异常任务不再只有“联系客服”的提示。导航中的 **人工处理**（`/manual`）提供最小处理闭环：

1. 失败任务卡或待人工核对卡 → 转人工处理，填写原因。
2. 系统持久化处理记录和当前会话对应的处理人。刷新后仍可看到记录；任务在人工处理期间不能继续或重试。
3. 填写核对说明，选择 **记录并结束自动处理** 或 **记录并继续任务**。
4. 继续仅适用于明确失败且不存在未决执行的任务。系统重试失败节点和其依赖节点，保留已成功节点；涉及写操作仍产生原有确认/MFA。
5. 接管和处理结论分别写入审计，和人工记录/任务状态同事务提交。审计失败则回滚该次处理。

## 事实与边界

- 人工说明不会把操作改成 `executed`，不会补造流水或修改余额。
- 结束自动处理会取消该失败计划的剩余未执行步骤，保留已成功节点和已入账交易。
- `needs_reconciliation` 表示执行结果不明，只能登记说明并结束自动处理；其交易状态继续保持待核对。**关闭人工处理记录不代表金融事实已经核清**。
- 失败的写节点必须有明确失败的操作结果；已提交转账凭证、未决确认、活跃执行和未知结果都会阻止人工选择重试。没有充分证据时，可停止并重新提出新的请求，不能从未知执行位置重跑。
- 当前是同一可信 Demo 会话中的人工操作席位，处理人从服务端会话/User 读取。没有真实银行客服、独立员工登录、角色分权或真实冲正流程。
- 独立操作的明确失败（如余额不足）也会出现在人工处理页，可记录说明并结束；调整金额等需求后由用户重新发起，不能在人工说明中修改原授权。
- 执行前若要修改金额/收款人，取消原确认并重新描述需求；已执行操作不提供账本“回退”。

## 实现与升级

- `agent/manual-review.ts`：人工处理业务与严格事务审计。
- `ManualReview`：处理人、原因、说明、结论、时间和关联任务/操作；`activeKey` 唯一约束限制一个目标只有一个活动处理记录。
- 计划状态认领及执行认领都在数据库条件中排除活动人工处理记录，不能仅靠前端隐藏按钮。
- `GET/POST /api/manual-reviews` 和 `POST /api/manual-reviews/[id]`：仅 Cookie 身份，校验会话与用户所有权，不注册为模型工具。
- 增量 schema 用既有 `npx prisma generate`、`npm run db:push -- --skip-generate` 流程应用；升级已有库无需清库或重新 seed。只有全新演示库才按 README 初始化种子。

## 验证

`tests/app/manual-review-http.test.ts` 经真实路由/DB/执行器验证人工接管、持久化、确认/MFA 保持、终态与余额/流水保持、跨会话拒绝、并发决定和审计回滚。

浏览器入口 `npx tsx tests/e2e/acceptance.e2e.ts` 的 `g-manual-handoff` 覆盖真实点击转人工、刷新保留、记录说明后继续仍等待确认，以及未知结果只能登记/结束。浏览器测试以隔离库中预置的查询失败/未知状态为起点，不声称通过浏览器制造了实际服务崩溃。

本轮实测：`npx tsc --noEmit`、全量 Vitest（109 文件 / 754 用例）、`npx next build`、真实 Chrome（7/7，0 跳过）均通过。隔离库从旧 schema 增量升级后，原用户、账户余额和流水保持不变，新增表可用。构建、升级、浏览器均使用隔离库，开发库文件保持原样。
