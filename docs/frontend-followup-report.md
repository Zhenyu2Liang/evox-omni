# 前端复查发现的四项问题修复与验收

目标分支：`genesis/agent_841944ee`；修复基线：`9f6f4b2`。本轮未修改其他分支，无数据库 schema 变更。

## 修复内容

1. **虚拟卡月限额未保存**：增加工具的 `monthlyLimit` 参数，安全网关校验金额，执行器传入 SDK，数据库保存到已有 `Card.monthlyLimit`。确认卡和成功摘要显示实际配置；没有限额时明确显示未设置。同一执行身份重放不重复开卡，改变限额的重放被拒绝。标签不作为额度约束的证据。
2. **解锁后旧 MFA 操作仍不可验证**：在已有的账号解锁事务中，恢复本用户仍处于 `awaiting_mfa` 的锁定挑战，次数归零；解除账号锁、恢复挑战和严格审计原子提交。终态操作和其他用户的挑战不受影响。解锁本身不执行业务，旧操作仍需正确验证码。
3. **赎回确认未展示金额**：服务端查询持仓，展示本金、全额赎回范围和到账金额，保存可信报价。业务事务重新读取金额，报价变化即停止并要求重新确认；同一计划节点复用原授权时保留原报价。模型不能自行指定可信报价。
4. **持仓名称/代码定位失败**：名称和代码解析使用实际状态 `HOLDING`，仍限定当前用户，多个匹配要求澄清。历史精确 ID 保留原执行身份的幂等重放能力。

## 能力边界

- 虚拟卡限额是持久化配置；Demo 没有刷卡支付接口，本轮不宣称已验证真实支付限额执行。
- 赎回仅支持整笔持仓全额赎回，不支持部分赎回。报价变化拒绝和名称/代码直接定位由确定性回归测试验证；真实模型本轮先查询持仓，再使用精确 ID。
- 解锁及 MFA 仍使用模拟验证码；未接入真实短信。解锁不等于业务授权完成。
- 本轮真实前端覆盖上述修复及小数转账回归，不作为全站所有功能或多实例安全证明。
- SQLite 的金额底层仍是 Float；本轮转账后原始余额为 `33408.57999999999`，界面与按分核对结果为 `33408.58`。未在本轮更换既有金额存储模型。
