## 修复结果

1. **提交后异常不再伪装为失败。** 正常确认、MFA 与恢复共同读取已提交的交易证据。转账已扣款但 SDK 返回路径抛错时，操作、审计和返回结果收敛为成功，不重新扣款。其他工具若已观察到事务提交、但无法证明结果，则进入 `needs_reconciliation`。
2. **历史流水可以核对恢复。** 没有 ExecutionReceipt 时，使用确定性流水 id，并核对用户、账户、方向、渠道、金额、备注和收款身份。匹配则补齐结果和审计；不匹配或凭证矛盾则人工核对。历史结果使用流水记录的姓名，不编造无法还原的原始余额。
3. **取消校验覆盖全部实际 SDK 写工具。** 服务端执行上下文将校验传到共同事务入口；计划/操作的条件写在业务变更前取得 SQLite 写入权。取消先提交则业务写被拒绝，业务先提交则保留真实结果。卡限额、冻结/解冻、挂失、虚拟卡、订阅、提醒、定时任务、预算和理财均纳入。
4. **转账关键审计与资金事实原子提交。** 必需的执行审计和扣款、流水、ExecutionReceipt 使用同一事务。关键审计插入失败时全部回滚，授权操作保留为可恢复状态。操作结果/状态在后续事务落地；历史缺失审计可以幂等补齐。审计去重核对业务身份，不能用相同 key 掩盖另一工具或相反结果。

另修正计划恢复/重试后的接口返回：重新读取持久化状态，避免取消竞争下返回状态与数据库不一致。
